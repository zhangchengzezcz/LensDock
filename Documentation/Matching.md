# 自动匹配与目录核查

本文件记录 2026-10-15 的开发源码。桌面的 `LensDock-0.1.0-preview-Retina.dmg` 与 GitHub `v0.1.0-preview` 仍对应提交 `9675545de729daf61e7cf3394d8de9f937452115`；未用开发模块覆盖已安装宿主或既有发布包。

## 身份与校准选择

- 保留 Lensfun 查询返回的所有兼容候选。库的 `LF_SEARCH_SORT_AND_UNIQUIFY` 是显示列表去重，会隐藏同名镜头的另一套传感器校准，不能用于唯一身份判定。
- 优先核对数据库记录的相机名称与别名。地区名称仅在厂商、卡口和正的有限裁切系数完全相同时视为等效；卡口或裁切模式不同仍需更多证据。
- 相机名称存在多个光学上下文时，可以用记录中的精确镜头身份区分兼容卡口。所有保留下来的候选必须共享相同相机光学上下文；相似焦距或未知镜头不能解除歧义。
- 同一个精确镜头身份有多套校准时，要求厂商和投影上下文一致，并在已知相机裁切系数的 3% 范围内只有一套校准。这个容差容纳 1.50 / 1.534 等记录舍入，不合并 1.0、1.5、1.6 和 2.0 传感器类别。不同鱼眼拟合仅在原始默认型号相同、标定比例相同、均属于鱼眼投影且传感器版本唯一时允许选择；直线/鱼眼冲突、共享翻译但原始型号不同、同尺寸多个候选仍拒绝自动选择。
- 仅有一个兼容的精确校准时，允许 Lensfun 按已知传感器尺寸缩放。并非所有镜头都必须用相同裁切系数拍摄标定；目录核查中的“指定版本是否相同”不能泛化为禁止正常缩放。
- XML 同一镜头的多个无语言标签名称均属于明确记录的身份。加载时把较早名称保留为内存中的私有语言别名，最后默认名称及原有显示翻译保留；光学标定和磁盘数据库不修改。共享别名对应多个光学记录时仍拒绝自动选择。

尼康 AF-P DX 10–20mm 配置的原始名称（包含 `168`）、最后默认名称和英文显示名称得到相同畸变及色差标定。没有新增任何根据内容猜测的畸变或暗角数据。

## 可重复核查

在项目根目录执行：

```sh
python3 Scripts/test.py
python3 Scripts/audit_catalog.py --run
```

目录核查从同一公共 XML 数据库生成小尺寸身份/插值样本。它对照镜头身份、相机裁切与卡口，并单独列出所选镜头校准的裁切系数、投影和比例是否与指定样本一致；输出在 `Build/Audit/catalog-audit-results.json`。生成输入和结果不含私人原片。

目录样本包含固定镜头 JPEG 相机和重复拍摄距离校准，**不代表 RAW 支持数量、实际镜头矫正准确率或 Lightroom 覆盖等效**。`Scripts/test.py` 对本地提供的 CR2、NEF、CR3 另做原生能力及部分实际匹配检查；照片不进入源码或发布包。

精简结果及源文件哈希在 `Evidence/identity-sensor-catalog-verification.json`、`Evidence/recorded-aliases-verification.json` 和 `Evidence/portable-suite-verification.json`。`camera-joint-catalog-verification.json` 是之前的中间步骤，只记录相机联合证据的效果，不作为最新版本的完整数量。

1566 个目录样本中，开发版本匹配 1563 个、拒绝 3 个；另外 5 个数据库条目缺少可生成样本的标定或兼容相机。匹配样本的相机卡口/裁切及镜头校准裁切、投影和比例均通过对照，没有选择不同指定校准版本的情况。

与已发布源码的 1537 个匹配相比，恢复了 26 个样本，无新增拒绝。之前保守拒绝的 Nikon 10.5mm 和 Sigma 10mm 鱼眼样本现能按同一原始型号、鱼眼上下文和唯一传感器版本区分；不同硬件身份及同尺寸投影冲突的拒绝测试仍通过。此前有 21 个样本选到不同裁切系数的标定；当前为 0。该对照检查的是目录指定版本，不能单独推断旧版本的全部 21 个渲染在光学上错误。

剩余 3 个自动目录样本是 Fujifilm F810 两条、Panasonic LX3 一条，原目录输入没有记录拍摄模式。LX3 有原始 RW2 传感器边界字段时已可识别模式，但不把另一个有模式字段的测试样本加到原目录通过数中。F810 的模式自动解析仍待验证，手动候选入口保留。

十四项开发测试组全部通过（渲染组另跑密集与网格两种布局，共 96 个组合），并实际运行本地 CR2、NEF、CR3 检查。开发原生面板整体编译、ad-hoc 签名验证通过。另在之前的隔离研究宿主构建完成 Nikon 已命名 PXD 的选择、应用、保存、关闭和重新打开；对应构建哈希见界面证据，不代表本次新匹配在所有 RAW、首保存或另一台 Mac 的验收。

## 原始拍摄模式证据

LX3 只采用原始 RW2 的 `IFD0:Sensor*Border` 及传感器尺寸判断 4:3、3:2、16:9 或 1:1，不用 JPEG 预览、编辑画布、XMP 裁切或 35mm 焦距猜测。边界必须是范围内的整数，比例匹配容差为 0.5%；数字变焦、额外裁切或非标准转换镜设置不能走此识别路径。当前 RAW 显影缓冲与记录比例若相差超过 1%，停止附加校正；原生支持时保留原生处理并禁用不确定的额外暗角。

这台固定镜头机身在标准镜头名称缺失时，只有原始字段明确记录 ExifTool 映射的 `Panasonic:ConversionLens = 1`（Off）、且库中只有一套兼容标准镜头配置，才以固定镜头身份补充匹配。不对可换镜头机身或未知转换镜状态采用此规则。

ExifTool 上游测试容器 `t/images/Panasonic.rw2` 的有效区域为 3648×2736，机型 LX3，转换镜设置为 1。实际字段读取及四种模式的合成边界测试已通过。来源提交与 SHA256、可重跑的纯元数据事实在 `Tests/Fixtures/LX3-capture-metadata.json`；容器不是完整可显影 RAW，不作为光学准确性或完整 RAW 流程的证据。新匹配尚未打入已发布 DMG，也尚未做 LX3 实拍的宿主渲染核查。

## 手动候选与保存

面板相机卡片中的“选择配置…”在已有匹配或有效 RAW 元数据读取后的匹配失败状态下可用。窗口分别搜索相机/拍摄模式和兼容镜头，显示厂商、裁切系数、比例及投影；原片匹配候选优先显示。正常已有匹配会预选当前配置，真正歧义不会默认选取第一套镜头标定。

确认所选配置只重新计算建议。点击“应用到 RAW”才写入可编辑效果；三个开关与强度独立保存。“恢复自动匹配”清除面板的手选标定并重新计算，仍需应用才能改动已保存效果。“重新匹配”明确重新读取原片并恢复自动识别；普通打开面板会保留文档已保存的手选配置和拍摄参数覆盖。

配置标识保存在 `metadata.LensDockProfileSelection.cameraID / lensID`。标识基于加载后的厂商/名称、卡口、相机模式/裁切和全部镜头标定点（包括投影、中心、比例），不使用数组位置、指针或查询得分。同一模型的标定点排序变化不使选择失效；混合校准模型的优先顺序保留在标识中，因为 Lensfun 采用首先遇到的模型。光学系数或模型优先顺序变更、缺失配置及不兼容卡口拒绝旧选择。手动选择不改写 `baseMetadata`、RAW 资源或原生矫正开关；原生支持仍跳过补充几何。

实际界面核查发现原生 `PTEffects` 的相同比较会忽略自定义滤镜档案中的配置变化。单纯调用 setter 曾让保存文件继续保留旧配置。现在 setter 核对图层真实回读；若被忽略，只暂时移除本项目效果并在同一次主线程调用中写入新效果，其他效果保留。最终回读通过后才登记历史；失败恢复原状态并报告。回归测试使用真实 PTFoundation 比较器及测试层 setter，验证无效成功、替换、其他效果保留和失败恢复。

修复后的 Nikon 测试副本在文件检查及重新打开界面中均保留手选相机/镜头标识；畸变、色差开启，暗角关闭，5,533,313 字节 NEF SHA256 不变。恢复自动匹配后，已保存文档索引仍未改变。范围与源/模块哈希见 `Evidence/profile-picker-ui-verification.json`；无 PXD、原片或渲染照片上传。

一张 Nikon NEF 的实际全尺寸保存预览已验证强度 100% → 50% → 撤销 → 重做的对应像素与原片哈希，见验收记录。仍需补充歧义模式的更多实际 RAW、完整实时渲染/历史事务核查及其他稳定性边界。手选能力不等同于 Lightroom 等量自动匹配。

## 拍摄参数自动读取与缺失恢复

正常照片先从 ImageIO EXIF 和 ExifTool MakerNotes 读取焦距、光圈与对焦距离，再自动匹配；详细设置自动填入这些记录，不要求用户逐项输入。已保存的显式参数覆盖优先，点击“恢复拍摄参数”才重新采用原始记录；手选的相机/镜头配置保留。

读取补充字段时保留 EXIF、MakerNote、轨道的分组信息，优先采用标准拍摄 EXIF，并保留 ImageIO 已读到的有效拍摄参数，避免同名 MakerNote 字段覆盖。真实 CR3 曾出现标准焦距 104 mm、Canon MakerNote 100 mm，旧流程误读为 100 mm，现已修复为 104 mm。MakerNote 的独立对焦距离仍可补充使用。

开发回归实际读取三份本地原片：CR2 为 17 mm、f/4；NEF 为 50 mm、f/7.1、距离约 2.37137 m；CR3 为 25 mm、f/5.6。三份均无需手填生成配置。没有距离记录时明确采用 1000 m 远距离标定回退，不声称这是实测距离。隔离宿主打开未修改 NEF 后，主面板与详细设置均自动显示相同参数，并标注 EXIF/MakerNotes 来源。证据见 `Evidence/capture-parameters-verification.json` 与 `Evidence/automatic-capture-ui-verification.json`。

2026-10-15 又只读检查本地 Lightroom 目录中的 821 张真实 CR3，代表一组 Canon EOS R50 V / RF100–400mm，含 27 组不同焦距与光圈。修复后逐张与目录的焦距和拍摄光圈记录独立对照，821/821 通过，全部无需手填生成匹配。原生支持时不生成额外几何映射，三项额外强度默认零、额外去暗角关闭；未读到对焦距离的 821 张均明确采用远距离回退。目录仅作为本地测试对照，产品运行不依赖 Lightroom。汇总见 `Evidence/private-raw-corpus-verification.json`；不含原图、路径或私人 EXIF 标识。这不等于 821 种镜头覆盖，也不证明光学精度或 Lightroom 等量覆盖。

只有读取到 RAW 元数据而未生成有效匹配时，才开放缺失参数补充；原片没有焦距就留空，不从镜头最短/最长焦距猜测。确认配置后如果仍缺焦距，待确认选择在面板内保留，可继续进入详细设置。未知光圈允许留空，仅停止依赖它的暗角补偿；已知焦距仍用于畸变与色差。未知值不显示为 f/0。清空的光圈或距离在效果序列化、恢复参数时保持缺失，不被原始字段悄悄补回；“恢复拍摄参数”则明确恢复原片记录。非法、非有限值及带单位尾缀的数字拒绝，支持系统地区的小数格式。

缺失恢复的原生插值、效果序列化及重载元数据回归已通过；测试过程中也用移除焦距的 CR2 副本走过选择、补全和生成建议。后者不算新增真实镜头自动匹配证据，且`55bf94e` 对应宿主构建的 GUI 证据仅覆盖未修改 NEF 自动填值。所有开发更改尚未进入既有 0.1 DMG；完整宿主保存/重开与光学准确性验收仍需继续。


### 实际拍摄光圈的备用字段

缺少有效 `FNumber` 时，现在会读取原始 EXIF `ApertureValue`。它记录拍摄时光圈，不能与 `MaxApertureValue` 或镜头名称中的最大光圈互换。有有效 `FNumber` 时优先保留该值；仅有最大光圈、范围描述或缺失/溢出的拍摄字段时，不生成拍摄光圈，也不启用暗角补偿。

ExifTool 的 `-n -ExifIFD:ApertureValue` 已做 ValueConv，输出为 f 值；ImageIO 的 EXIF 字典仍是 APEX，按 `2^(APEX/2)` 转换一次。APEX 0 按标准为 f/1，不能因为数值为零而视为缺失。不会将 ExifTool 的结果再次做指数换算。

`Tests/verify-recorded-aperture.m` 现场生成只含测试 EXIF 的小型 TIFF 容器，验证两种真实读取路径、优先级、最大光圈拒绝、零 APEX、溢出及零 `FNumber` 的恢复，并验证可自动生成配置。此容器仅用于元数据回归，与产品 RAW 编辑流程无关。旧提交 `55bf94e` 在 APEX-only 案例中复现缺失，新实现通过六种案例的十二个读取组合；十四组完整回归通过，本地 CR2/NEF/CR3 读取仍通过。精简证据在 `Evidence/recorded-aperture-verification.json`。这不增加已确认的真实镜头数量，也不是新字段的宿主 GUI、完整 RAW 或光学准确性验证。
